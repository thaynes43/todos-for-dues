## 1. Goal

Implement DESIGN-001 end-to-end: every Drizzle schema file in `packages/db/src/schema/`, the initial `drizzle-kit`-generated migration, and the hand-written migrations for required Postgres extensions and the ADR-011 deferred-CHECK min-Admin trigger. Verify by integration tests that exercise every CHECK + index + trigger.

> **Produces:** complete Drizzle schema for the walking-skeleton subset (8 tables) + 4 migrations applied cleanly to a fresh PG16 + an integration test suite at `packages/db/__tests__/` that passes against testcontainers.
> **Definition of success:** running `drizzle-kit migrate` against a fresh Postgres database produces all tables in DESIGN-001 §3 with their constraints + indexes + the min-Admin trigger; `pnpm --filter @app/db test` passes all integration tests including the constraint-violation cases in DESIGN-001 §8.

## 4. Steps

### Step 1 — Add Drizzle schema files (one per table)

- **Action:**
  - Create each file under `packages/db/src/schema/` matching DESIGN-001 §4 verbatim. Honor every CHECK, every NOT NULL, every default, every index, every foreign key.
  - Update `packages/db/src/schema/index.ts` barrel to export all schemas.
  - For each schema file, also generate the `drizzle-zod` insert + select schemas (used by tRPC procedures in PLAN-005). Add `drizzle-zod` to `packages/db` deps.
- **Verification:**
  - `pnpm --filter @app/db typecheck` passes.
  - `import { users, jobs, ... } from '@app/db'` resolves at the consumer side.
- **Resume note:** schema declared but no migrations yet.

### Step 2 — Generate initial migration

- **Action:**
  - Run `pnpm --filter @app/db drizzle-kit generate --name=init`. Inspect the generated `0001_init.sql`.
  - Verify it matches the expected output (every table from §4 with the right columns + indexes + CHECKs). If anything is off (e.g., Drizzle didn't generate a particular CHECK as written), adjust the schema file to use Drizzle's exact syntax for that constraint and regenerate.
  - Commit-test only: do not yet run migrations.
- **Verification:** `0001_init.sql` exists and references all 8 tables.
- **Resume note:** generated migration in place, not yet applied.

### Step 3 — Add hand-written migrations

- **Action:**
  - Add `packages/db/migrations/0002_extensions.sql`:

    ```sql
    CREATE EXTENSION IF NOT EXISTS pgcrypto;
    ```

  - Add `packages/db/migrations/0003_min_admin_trigger.sql` — verbatim from DESIGN-001 §5.3.
  - Update Drizzle's migration journal (`meta/_journal.json`) to include 0002 and 0003. Refer to Drizzle docs for the exact format; the agent verifies by running migrations against a fresh DB.
- **Verification:** `pnpm --filter @app/db drizzle-kit migrate` against a fresh Postgres applies all 4 migrations cleanly (in order: 0002 extensions, 0001 init — note that extensions must run BEFORE init since `gen_random_uuid()` is from pgcrypto). **Reorder if needed**: rename 0001 → 0003, 0002 → 0001 (extensions), or use Drizzle's `before` hook. Document the chosen ordering.

  > **Important fix:** The original DESIGN-001 §5 ordered extensions as `0002`, but `gen_random_uuid()` is referenced in `0001_init.sql`. The actual ordering must be: extensions FIRST, then init, then trigger. The agent renumbers as needed and documents the final ordering.

- **Resume note:** migrations applied; schema visible in psql.

### Step 4 — Write the migration-application integration test

- **Action:**
  - `packages/db/__tests__/migrations.test.ts`:

    ```ts
    import { describe, it, expect, beforeAll, afterAll } from 'vitest';
    import { startPostgres } from '@app/test-utils';
    import { migrate } from 'drizzle-orm/node-postgres/migrator';
    import { drizzle } from 'drizzle-orm/node-postgres';
    import { Pool } from 'pg';

    describe('migrations', () => {
      let stop: () => Promise<void>;
      let url: string;
      beforeAll(async () => { ({ url, stop } = await startPostgres()); });
      afterAll(async () => { await stop(); });

      it('applies cleanly to a fresh Postgres', async () => {
        const pool = new Pool({ connectionString: url });
        const db = drizzle(pool);
        await migrate(db, { migrationsFolder: './migrations' });

        // Sanity: every expected table exists
        const tables = await pool.query<{ tablename: string }>(`
          SELECT tablename FROM pg_tables WHERE schemaname = 'public' ORDER BY tablename
        `);
        expect(tables.rows.map(r => r.tablename).sort()).toEqual([
          'chapter_settings',
          'invite_tokens',
          'job_enrollments',
          'job_state_transitions',
          'jobs',
          'user_role_transitions',
          'users',
        ]);

        await pool.end();
      });
    });
    ```

- **Verification:** `pnpm --filter @app/db test` passes.
- **Resume note:** migrations proven correct end-to-end.

### Step 5 — Write the constraint-enforcement integration tests

- **Action:**
  - `packages/db/__tests__/constraints.test.ts`:
    - **Per-CHECK tests:** insert a row that violates each CHECK; expect ERRCODE `23514`.
      - `users.role` not in enum
      - `users` with both `passwordHash` and `oidcSubject` null
      - `jobs.duesAmount = 0`
      - `jobs.recommendedPeopleCount = 0`
      - `jobs.description = ''` (after trim)
      - `jobs.state` not in enum
      - `invite_tokens.preselectedRole` not in {'Active', 'Alumni'}
    - **UNIQUE tests:** insert two `users` with the same email; expect ERRCODE `23505`.
    - **FK ON DELETE CASCADE:** delete a `users` row → its `job_enrollments` rows are gone.
    - **Partial index sanity:** insert 1000 `job_state_transitions` rows of various states; query disputed jobs; assert the index is used (EXPLAIN).
  - `packages/db/__tests__/min-admin-invariant.test.ts`:
    - Insert one user with role 'Admin'; attempt to demote → ERRCODE `23514` mapped to "min-Admin invariant violated".
    - Atomic swap (single transaction): promote B to Admin AND demote A to Alumni → succeeds at COMMIT.
    - INSERT a second Admin (so count is 2); demote one → succeeds.
    - DELETE the only Admin user → the trigger fires and rejects.
- **Verification:** all tests pass.
- **Resume note:** constraints proven enforceable.

## 7. Risks & gotchas

- **Risk:** `gen_random_uuid()` requires `pgcrypto`. The init migration uses it, so the extension must exist FIRST. **Mitigation:** Step 3 explicitly handles ordering.
- **Risk:** Drizzle's CHECK constraint syntax may differ slightly from the SQL in DESIGN-001 §4. **Mitigation:** review generated SQL in Step 2 and adjust the Drizzle declaration if the produced CHECK doesn't match intent.
- **Risk:** The deferred-CHECK trigger must be `INITIALLY DEFERRED` for the atomic-swap test to pass. If `INITIALLY IMMEDIATE`, the trigger fires per-row and the swap fails. **Mitigation:** verbatim SQL from DESIGN-001 §5.3 + Step 5's atomic-swap test catches mistakes.
- **Risk:** `drizzle-kit generate` may emit constraints in an order that conflicts with FK references. **Mitigation:** review and reorder in the generated SQL if needed (rare; usually Drizzle does the right thing).
- **Risk:** Better Auth's tables are NOT in this schema; `drizzleAdapter` adds them on first call to `auth.handler` at app boot. This means the test DB has fewer tables than the prod DB after first auth use. **Mitigation:** integration tests for auth (PLAN-004) initialise Better Auth in `beforeAll` to create those tables; this plan's tests don't need them.
